# Grammar-constrained decoding in htpd: design (patch written, not built or deployed)

## 1. What htpd already has (v7, no build needed)
- `HTPD_PATTERN_TRIE=2` already constrains greedy decoding, per stream, inside labelled top-level string values.
  - With no request labels, the labels come from the prompt's own `JSON keys: pattern (a|b|…), status (…), likely_cause (…)` list.
  - That list is built per role, so the labels are per role.
  - `HTPD_TRIE_KEYS` selects the keys (default `pattern,status`).
- Its output is identical to plain greedy whenever the greedy token is on-label. When it is not, the highest-logit on-label token is used instead.
- **This already fixes the board's off-label cause** (water `acidic_condition` → rejected → solo re-run).
  - It needs only a profile line, on an htpd ≥ v7 binary:
    `env=HTPD_PATTERN_TRIE=2 HTPD_TRIE_KEYS=pattern,status,likely_cause`
  - The line changes the htpd args, so htpd restarts once. Keep to one NPU client at a time.
  - Cost: one label check per token, on precomputed pieces. When greedy is off-label, the top 64 candidates are checked, with a full scan as fallback.
- **Gaps of the trie:**
  - It does not see `fault_kind`, because the prompt-label key list in htpd.cpp is `pattern,status,likely_cause,action`.
  - It cannot couple fields: `fault_kind` must appear exactly when status is `sensor_fault`, and the cause must be `sensor_fault` exactly then.
  - It cannot enforce the observation format: 1–2 strings, each ending in a `[E1..E10]` citation.

## 2. Patch `htpd_grammar_v9.patch` (100 changed lines, applies to the current htpd.cpp; syntax-checked on the host with the 620d222 headers; not built for the board)
- **New env flag `HTPD_GRAMMAR=1|2` (default 0 = byte-identical v8 behaviour):**
  - `1`: the request carries `"grammar": ["<GBNF>" | null, …]`, aligned with `prompts`.
  - `2`: the same, else the role file `HTPD_GRAMMAR_DIR/agent_v2_<role>.gbnf`, chosen from the system prompt's `You are the <Role> agent` line.
- **Per stream:** `StreamOpt.grammar` is a clone (`llama_sampler_clone`) of a prototype parsed once per distinct GBNF text (`llama_sampler_init_grammar(vocab, gbnf, "root")`).
  - Parse: 0.1–1.7 ms. Clone: 20–130 µs (host).
- **`pick()` = the existing label/trie pick, then `grammar_pick()`. It is lazy, the same scheme as llama-server's `grammar_first`:**
  1. Test the chosen token alone: `llama_sampler_apply` on a 1-candidate array.
  2. If it is allowed, `llama_sampler_accept` it and return it. This is the accept path.
  3. Otherwise, mask the full vocabulary: `llama_sampler_apply` on all 128,256 candidates. Take the highest-logit allowed token (first index on ties), count it as `forced`, and accept it. This is the reject path.
- **Drafting (`HTPD_DRAFT=1`) stays exact:** the draft-verification loop calls `pick()` row by row and consumes every result, stopping after the first mismatch. Accepting inside `pick()` therefore keeps the grammar state in step with the text.
- **The stop rule is unchanged:** the stream still stops at the top-level `"action"` key. The grammar describes the full answer through `"action": "<enum>"}`, so it never reaches an end state before the stop.
- **Also in the patch:** `fault_kind` is added to the prompt-parsed label keys, so `HTPD_TRIE_KEYS=…,fault_kind` works with the trie alone.

## 3. The grammar (`../grammar/agent_v2_<role>.gbnf`, generated by `scripts/gbnf_v2.py` from the v2 label registry)
- It covers the continuation after the prefill `{"pattern": "`.
- It fixes the key order and spacing of the training targets.
- It allows only the role's patterns, `normal|warning|critical|sensor_fault`, the role's causes and actions, and the 7 fault kinds.
- `sensor_fault` ⇔ `fault_kind` present ⇔ cause `sensor_fault`. This holds for all 696 gold `sensor_fault` rows of test + rw5test + dev.
- Observations: 1–2 strings, each ending in an `[E1..E10]` citation (all 2,236 gold observations of the 1,466 test + rw5test rows match).
- Values: confidence `0.x[x]`, a bool, onset `HH:MM`.

## 4. Cost
Measured on the host (x86 laptop, WSL, llama.cpp 620d222, vocab-only micro-benchmark `bench_grammar.cpp`, 12 real v2 answers of all 6 roles, run beside a 4-thread llama-server):

| path | when | host cost |
|---|---|---|
| accept (1 candidate + accept) | every generated token | 41–98 µs per token (median ≈ 70) |
| reject (full 128k mask) | only when greedy is off-grammar | 23–38 ms mean per position (max 113 ms, inside free-text observations where 18–43k tokens are allowed) |
| parse + clone | once per GBNF / per stream | 0.1–1.7 ms / 20–130 µs |

- All 12 stored answers were on-grammar at every token, so the reject path never ran.
- **Board estimate:**
  - ARM CPU cores are slower than the laptop core: assume 2–3×.
  - Accept path: ≈ 0.15–0.2 ms per token per stream. A 13-stream decode step adds ≈ 2–3 ms against a ≈ 150–200 ms NPU step (16.4 s per 13-agent batch at ≈ 90 tokens). That is ≈ 1–2 % wall time, on the CPU, serial with the decode loop.
  - Reject path: ≈ 60–110 ms per forced token, and only on off-label answers. On the board that is the `acidic_condition` case: ~2–4 forced tokens, ≈ 0.2–0.4 s. That replaces a 2.5–3.5 s solo re-run plus a rejected answer.
- **How to shrink the accept path if 1–2 % matters:**
  - Apply the grammar only while inside an enum value (a lazy grammar), or use the trie for enums and the grammar only for structure.
  - Or check the token with `llama_grammar_accept` on a stack copy instead of `llama_sampler_apply`.
- Host A/B of the full grammar against unconstrained decoding (accuracy, JSON, ms per token): see `../RESULTS.md` §1 and `../grammar_tables.md`.

## 5. Rollout order (main deploys)
1. **No build:** turn the trie on through the profile, on an htpd v7+ binary:
   `env=HTPD_PATTERN_TRIE=2 HTPD_TRIE_KEYS=pattern,status,likely_cause`.
   - Check with the chaos run: no `cause … not allowed` rejections, and `forced` > 0 in `htpd.log` only on those answers.
2. **Optional, with a build:**
   1. Apply `htpd_grammar_v9.patch` and build it as `htpd_v9` (`build_htpd.sh`).
   2. Push the 6 `.gbnf` files with the app stopped (`.part` + md5 + mv).
   3. Set the profile: `bin=…/htpd_v9`, `env=HTPD_GRAMMAR=2 HTPD_GRAMMAR_DIR=<dir>`.
   4. Compare one full chaos run and the 54-window device set with and without the grammar.
